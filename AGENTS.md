# GrocerMate agent guidance

When generating or refactoring Dart code, use the [GrocerMate Flutter skill](.agents/skills/grocer-mate-flutter/SKILL.md) and follow these conventions.

- Read the current working tree before editing. Review relevant staged, unstaged, and untracked changes. Build on those edits and preserve unrelated work.
- Keep composition in `lib/main.dart`, startup and shared dependency wiring in `lib/core/injection`, and routing in `lib/core/routing`. Keep feature and module registrations next to the code they wire. Keep shared platform services under `lib/core` and controllers and widgets in the feature that owns them, including `lib/features/app` for app presentation.
- Expose one shared `injector` instance from `lib/core/injection/dependencies.dart` and use a `Future<void> initializeDependencies()` startup function for app-wide needs without returning the injector or passing factory functions through `GrocerMateApp` and `createAppRouter`. Provide `AppConnectionCubit` inside `GrocerMateApp` and resolve feature dependencies directly from `injector` when the destination builds or the operation needs them. Keep tap handlers limited to navigation and put controller providers at the smallest route or shell that shares their state.
- Centralize route paths, route names, and global navigator keys (`rootNavigatorKey`, `shellNavigatorKey`) in `RoutesConstants` (`lib/core/routing/routes_constants.dart`). Use a single `ShellRoute` for `MarketHome` (providing `ShoppingBloc` and `CatalogBloc`), open full-screen sub-routes such as `ProductScreen` on `rootNavigatorKey` while sharing `ShoppingBloc` via `BlocProvider.value`, and avoid nested `ShellRoute`s or `StatefulShellRoute.indexedStack` when per-tab navigation stacks are unnecessary. Separate distinct screens (such as `CartScreen` and `SavedScreen`) into dedicated widgets and extract shared UI into a reusable widget.
- In routing and UI files that contain multiple distinct sections, routes, providers, listeners, or widget blocks, separate each section with a comment in the format `//------------ Section Name ---------------` and leave an empty line before and after each block for readability. Do not add section comments to simple single-element or single-segment widgets.
- Extract complex multi-condition boolean expressions (such as 3+ condition checks in `listenWhen`, compound filter predicates, or nested validation guards) into named `bool` variables (e.g., `isNotInitialLoad`, `hasNewReview`, `hasNewOrder`) with a brief single-line comment above each part explaining what it checks. Keep simple 2-part checks inline (e.g., `if (_loading || isClosed) return;`, `if (scheme == 'http' || scheme == 'https')`).
- Keep GetIt behind `Injector`. Use the shared registration helper for lazy singletons and factories, and keep feature factories focused on wiring their dependencies. Give each route controller a fresh instance and pass route parameters at resolution time.
- Let controllers handle loading, retries, and state. Keep repositories out of widget context and keep the root provider scope for app-wide state.
- Isolate a third-party package behind a small interface and one adapter when callers need to be package-independent. Use the package's existing behavior and ordinary Dart values at the boundary. For example, `ConnectionChecker` exposes a boolean status and `PlatformConnectionChecker` owns the `connectivity_plus` import.
- Pass the smallest dependency the caller needs. Use `() => connection.online` for a live read and pass a stream where a consumer reacts to changes. Use direct names and introduce a class, interface, package, or global widget only when it serves a concrete requirement.
- Prefer the framework's built-in behavior. Keep parsing, normalization, and validation at the boundary that owns the input, and add checks only for supported inputs or concrete failure cases. Keep the implementation as small as the behavior allows.
- Use `Endpoints` for API paths and `json_serializable` for models with both `fromJson` and `toJson`, keeping one model class per file under `data/models/`. Share a generic response model when the API uses a common envelope, call `Model.fromJson` and `model.toJson()` directly instead of standalone `decode*`/`encode*` helpers, and introduce a separate domain entity only when a model needs domain validation, UI input rules, or converted units/fields.
- Let controllers subscribe when created and cancel subscriptions when closed. Wait at startup only for required app-wide state, such as connectivity for a cold deep link. Keep offline behavior and reconnect retries independent of connectivity feedback in the UI.
