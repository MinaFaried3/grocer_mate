# GrocerMate Flutter

1. Inspect `git status --short`, the relevant `git diff` and `git diff --cached` output, and any relevant untracked files. Follow the current code and the user's latest direction when the branch and working tree differ.
2. Trace the real entry point and choose the owner before editing. Read `lib/core/routing/app_router.dart` and `lib/core/routing/routes_constants.dart` for route paths, global navigator keys, and shell lifetimes, and read the owning feature or module for its factories. Read `lib/core/injection/dependencies.dart` for the shared `injector` and `Future<void> initializeDependencies()` startup function. Provide `AppConnectionCubit` inside `GrocerMateApp` and resolve dependencies directly from `injector` in routing and UI factories without passing factory callbacks across constructors. Browse and product details own separate controllers. The single `MarketHome` `ShellRoute` provides `ShoppingBloc` and `CatalogBloc` across Browse, Cart, and Saved, while `ProductScreen` opens on `rootNavigatorKey` and receives `ShoppingBloc` via `BlocProvider.value`.
3. For injection changes, keep GetIt inside `GetItInjector`, expose the shared `injector` from `dependencies.dart`, and use the `Injector` methods from feature wiring. Reuse the register-once helper for shared services and factories. Check that startup still skips unused dependencies, shared services keep their identity, and parameterized factories receive the current route argument.
4. Make the smallest change that preserves existing callers. In routing and UI files that contain multiple distinct sections, routes, providers, listeners, or widget blocks, separate each section with `//------------ Section Name ---------------` comments and leave an empty line before and after each block for readability (skip section comments on single-element or single-segment widgets). Extract complex multi-condition boolean expressions (such as 3+ condition `listenWhen` checks, compound filter predicates, and multi-part validation guards) into descriptive named `bool` variables (e.g., `isNotInitialLoad`, `hasNewOrder`) with a concise comment above each part, while keeping simple 2-part checks inline. Keep distinct screens as separate widgets (such as `CartScreen` and `SavedScreen`) backed by reusable widgets for shared layout. Prefer built-in framework behavior, such as Dio base URLs and query parameters. Normalize inputs once and add validation for a concrete requirement at the boundary that owns it. A product route can create its controller in `BlocProvider.create` and let the controller load data. A repository that only reads connectivity can accept `bool Function()` while a bloc that retries on reconnection can also accept a `Stream<bool>`. Keep platform imports in the adapter so controller tests can supply a fake. For endpoint and model changes, use `Endpoints` and give each model its own file with generated `fromJson` and `toJson` methods via `json_serializable`. Call `Model.fromJson` and `model.toJson()` directly rather than writing standalone `decode*` or `encode*` functions, use a generic response model only where the wire format has a shared envelope, and add a separate domain entity only when validation, UI rules, or converted units/fields require it. Run `dart run build_runner build` after changing models.
5. Verify the affected behavior through its normal entry point. For startup or routing changes, check cold deep links, route-local initialization, and state shared across tabs. For connection changes, check cached reads, manual Offline mode, and queued checkout replay where affected. Run `dart format` on changed Dart files, `flutter analyze`, and the relevant `flutter test` cases. Verify runtime lifecycle changes with a Flutter hot reload or restart when available.

The [repository rule](../../../AGENTS.md) defines the conventions this workflow applies.
